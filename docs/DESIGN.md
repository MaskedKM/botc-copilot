# 🩸 血染钟楼对局助手 App — 产品设计文档

> 核心定位：不是电子笔记本，而是**推理引擎辅助工具**。
> 理解 BotC 的信息网络结构，帮助玩家记录 → 结构化 → 交叉验证 → 推理分析。

---

## 一、BotC 的信息推理本质

### 1.1 这不是狼人杀

狼人杀靠"发言状态"和"逻辑基线"推理。BotC 完全不同——**每个角色都是一个信息节点，角色间的信息交叉构成推理网络**。

### 1.2 五大核心推理公理（来自 botc-ai-copilot 项目）

| 公理 | 内容 | 对 App 的启示 |
|------|------|--------------|
| **伪装排他** | 恶魔的 3 个 Bluff 角色物理上不在场，宣称即假 | App 应维护"已声明角色 vs 可能在场角色"列表 |
| **座位收缩** | 死人从邻座计算中物理移除，两侧存活者直接并拢 | 座位图必须支持动态收缩，Empath 信息自动重算 |
| **醉毒一命** | 一次性技能（Slayer 等）在醉/毒时发动=永久失效 | 需追踪一次性技能使用状态 × 醉毒状态 |
| **恶魔传承** | 恶魔传给已死玩家=邪恶立刻战败 | 恶恶魔死亡后需标记"传承是否可能" |
| **角色唯一** | 同一好人角色至多 1 个，两人宣称同角色必有假 | 自动冲突检测：同角色多人声明 → 高亮标记 |

### 1.3 两种核心推理范式

**单链逻辑 (Single-Chain Logic)**
> 假设 A 为真 → 推导 B → 推导 C → 如果结论自洽则 A 大概率为真

例：掘墓人报处决者身份 → 验证被处决者的声明是否真实 → 如果验证通过，被处决者的信息也可信 → 继续传导

**双链逻辑 (Double-Chain Logic)**
> A 和 B 互斥 → 分别假设 A 真/B 真 → 各自推导 → 比较哪个结论更合理

例：两人都声称是 Chef，给出不同数字 → 假设 A 真：B 的邻居都是好人 → 假设 B 真：A 的一个邻居是邪恶 → 两种情况都产生新信息

### 1.4 信息树结构与"打断根节点"

官方设计师 Steven Medway 的核心洞察：

```
事实 A + 事实 B → 事实 C + D + E + F → 指向恶魔身份
```

**打断 A 或 B（根节点）远比打断 C/D/E/F（叶子）有效。**

App 的核心价值：**可视化这棵信息树，帮玩家找到"根节点"在哪。**

## 二、对局中需要记录的信息（完整分类）

### 2.1 静态信息（开局一次性输入）

| 数据 | 说明 | 推理用途 |
|------|------|----------|
| 玩家列表 | 所有参与者名字 | 基础索引 |
| **座位顺序** | 马蹄形排列，按顺时针 | Empath/Chef/邻座计算的基础 |
| 剧本 | TB / BMR / S&V / 自定义 | 确定角色池 |
| 玩家数 | 5-15 人 | **决定邪恶数量、外来者数量** |
| **外来者数** | 由玩家数查表得出 | 推断 Baron 是否在场、Drunk 是否可能 |
| **我的角色** | 自己的身份和能力 | 确定自己的信息源 |

**玩家数 → 邪恶/外来者对照表（TB 基准）**

| 玩家数 | 镇民 | 外来者 | 爪牙 | 恶魔 |
|--------|------|--------|------|------|
| 5 | 3 | 0 | 1 | 1 |
| 6 | 2 | 1 | 1 | 1 |
| 7 | 3 | 1 | 1 | 1 |  ← 修正：应为 3T/1O/1M/1D（共6好1恶+...），实际 TB: 5人=3T/0O/1M/1D
| 8 | 3 | 2 | 1 | 1 |
| 9 | 5 | 0 | 1 | 1 |  ← 修正：9人=5T/0O/2M/1D
| 10 | 5 | 1 | 2 | 1 |
| 11 | 5 | 2 | 2 | 1 |
| 12 | 7 | 0 | 2 | 1 |
| 13 | 7 | 1 | 2 | 1 |
| 14 | 7 | 2 | 2 | 1 |
| 15 | 9 | 0 | 3 | 1 |

> ⚠️ 注意：不同剧本的配置表略有不同。App 应内置各剧本的配置表。

### 2.2 动态信息 — 按天/夜记录

这是 App 的**核心数据层**。每一天包含以下子记录：

#### 夜晚阶段

| 数据 | 说明 | 推理用途 |
|------|------|----------|
| **死亡事件** | 夜间谁死了 / 无人死 | 排除恶魔候选；无人死=Monk保护/Soldier/恶魔自杀 |
| **我的信息** | 自己角色获得的信息（如 Empath 数字、占卜 yes/no） | 个人推理基础 |
| **他人信息声明** | 白天时他人公开的信息 | 交叉验证 |

#### 白天阶段

| 数据 | 说明 | 推理用途 |
|------|------|----------|
| **角色声明** | 谁公开声明什么角色 | 建立信息网络；检测重复声明 |
| **信息声明** | 角色获得的具体信息内容 | 如 Chef=1, Empath=0, 占卜选 A+B = yes |
| **行为备注** | 可疑行为、私下交流内容、语气变化 | 软信息，辅助判断 |
| **提名记录** | 谁提名了谁 | 提名模式分析 |
| **投票记录** | 每人投了谁、赞成/反对、是否使用死票 | **高价值**：投票模式暴露阵营 |
| **处决结果** | 谁被处决 | 改变存活人数、触发掘墓人信息 |
| **身份揭示** | 处决后掘墓人报的身份 / 游戏结束揭示 | 验证/推翻之前的假设 |

### 2.3 推理层信息（App 的核心差异化）

这不是原始数据，而是**基于原始数据推导出的判断**：

| 推理项 | 说明 |
|--------|------|
| **信任度评分** | 对每个玩家的好坏倾向判断（好/偏好/未知/偏坏/坏） |
| **角色可能性** | 每个玩家可能是什么角色的候选列表 |
| **信息可靠性** | 某玩家信息是否可能被醉/毒影响 |
| **矛盾标记** | 两个信息声明之间的逻辑冲突 |
| **逻辑链** | 用户记录的推理过程："如果 A 真→B 真→C 真" |
| **恶魔候选** | 当前最可能的恶魔候选人列表（随信息更新收缩） |
| **好确信名单** | 已确认/高度确信为好人的玩家列表（排除法推理基础） |

### 3.2 核心功能详细设计

#### 功能 1：动态座位圆环 ⭐

**这是 UI 核心。** 不是静态列表，而是可交互的马蹄形座位图。

- **圆环布局**：玩家按实际座位排列成马蹄形
- **状态标记**：存活（正常）/ 死亡（灰化+骷髅）/ 自己（高亮标记）
- **信任色标**：每个玩家头像周围用颜色环标记信任度（绿=好/黄=未知/红=嫌疑）
- **点击展开**：点击任意玩家 → 弹出该玩家的完整信息卡
- **动态收缩**：死亡玩家变灰但仍占位，Empath 邻座计算时自动跳过
- **邻座高亮**：选中某玩家时，高亮其当前存活邻座

#### 功能 2：每日信息记录卡 ⭐

按"天"为单位的结构化记录，而非自由文本。每天包含：

```
Day N
├── 夜晚
│   ├── 死亡：[选择玩家 / 无人死亡]
│   ├── 我的信息：[根据角色自动提供对应输入模板]
│   └── 夜晚备注：[自由文本]
├── 白天
│   ├── 角色声明表：每人声明什么角色（快捷选择）
│   ├── 信息声明表：每人报了什么具体信息（结构化）
│   ├── 提名 & 投票：谁提名谁 → 赞成/反对票数 → 结果
│   ├── 处决：[选择玩家 / 无处决]
│   └── 行为备注：[自由文本，按玩家标记]
└── 日终推理快照
    ├── 信任度更新（滑块快速调整每人）
    └── 恶魔候选更新
```

**关键设计：信息输入模板按角色自动适配**

| 角色类型 | 输入模板 |
|----------|----------|
| Chef | 数字输入（0-N） |
| Empath | 数字输入（0-2） |
| Fortune Teller | 选 2 个玩家 + yes/no |
| Investigator | 选 1 个爪牙角色 + 选 2 个玩家 |
| Washerwoman | 选 1 个镇民角色 + 选 2 个玩家 |
| Undertaker | 选 1 个角色名（被处决者身份） |
| 自由文本 | 通用文本框 |

#### 功能 3：推理引擎 ⭐⭐⭐（核心差异化）

这是现有工具都没有的功能，是 App 的灵魂：

**3a. 自动矛盾检测**

系统根据已记录的信息声明，自动检测逻辑冲突：

- **角色重复声明**：两人声明同一角色 → 高亮 + "至少一假"
- **外来者数量冲突**：声明的外来者数 ≠ 应有数量 → 提示 Baron/Drunk 可能
- **Empath 数字 vs 声明阵营**：如 Empath 报"邻居有 1 邪恶"，但两人都声明好人角色 → 标记矛盾
- **Chef 数字 vs 座位分析**：根据座位和已知邪恶，验证 Chef 数字是否合理
- **占卜结果 vs 死亡模式**：占卜说某对有恶魔，但恶魔杀了其中一人 → 标记

**3b. 信息可靠性追踪**

对每个信息源标记可能的"污染"状态：

- 🟢 **可信**：信息提供者已验证（如被掘墓人确认）
- 🟡 **待验证**：信息提供者声明未确认
- 🔴 **可能污染**：该玩家可能被毒/醉（如已知 Poisoner 在场，或外来者数量异常）
- ⚫ **已失效**：该玩家被毒的那一夜的信息

**3c. 排除法追踪器**

核心推理辅助：维护"确定好人"和"恶魔候选"两个动态列表。

- 随着信息增加，自动将玩家在"未知 → 偏好 → 确信好人"或"未知 → 嫌疑 → 恶魔候选"之间移动
- 最终目标：缩小恶魔候选到 1-2 人

**3d. 逻辑链笔记**

用户可以记录自己的推理链：

```
假设：掘墓人是真的
  → 被处决的 A 确实是 Poisoner
    → A 给我的信息是假的
      → A 说 B 是邪恶 → B 可能是好的
结论：B 偏向好人
置信度：中（掘墓人本身可能被毒）
```

App 提供结构化的逻辑链编辑器，支持"假设→推导→结论→置信度"格式。

#### 功能 4：投票分析 ⭐

投票模式是 BotC 中信息量最大的行为数据之一：

- **投票时间线**：每天每轮投票的可视化记录
- **阵营暴露**：邪恶玩家倾向于保护彼此（不投同伴）、集中票数推好人
- **异常投票检测**：标记"反常"投票（如某人突然改变投票倾向）
- **死票使用**：追踪死亡玩家的投票使用情况

#### 功能 5：角色信息交叉矩阵 ⭐

一个矩阵视图：行是玩家，列是角色，单元格标记"声明/已确认/排除"。

帮助快速回答：
- 哪些角色还没人声明？（可能是恶魔的 Bluff 或隐藏好人）
- 哪些角色被多人声明？（冲突点）
- 已确认的角色有哪些？（信息链的可靠起点）

#### 功能 6：复盘模式 ⭐

游戏结束后：

- **时间线回放**：按天回放所有事件
- **信息树可视化**：展示信息之间的依赖关系
- **推理审计**：回顾自己的判断哪里对了/错了
- **关键转折点**：标记游戏转折的决策点

## 四、数据模型设计（草案）

```typescript
// 核心实体

interface Game {
  id: string;
  script: Script;           // TB / BMR / S&V / custom
  playerCount: number;
  players: Player[];        // 按座位顺序
  myRole: Character;
  days: DayRecord[];
  setup: GameSetup;         // 邪恶数、外来者数等
  status: 'ongoing' | 'good_win' | 'evil_win';
}

interface Player {
  id: string;
  name: string;
  seatNumber: number;
  alive: boolean;
  deathDay?: number;
  deathCause?: 'night_kill' | 'execution' | 'other';
}

interface DayRecord {
  dayNumber: number;
  night: NightRecord;
  day: DayPhaseRecord;
  endSnapshot: ReasoningSnapshot;
}

interface NightRecord {
  deaths: PlayerId[];       // 夜间死亡，空数组=无人死
  myInfo?: CharacterInfo;   // 我获得的信息
  notes?: string;
}

interface DayPhaseRecord {
  claims: RoleClaim[];      // 角色声明
  infoDeclarations: InfoDeclaration[]; // 信息声明
  nominations: Nomination[];
  execution?: PlayerId;
  undertakerResult?: Character;  // 掘墓人信息
  behavioralNotes: BehavioralNote[];
}

interface RoleClaim {
  playerId: PlayerId;
  character: Character;
  day: number;
  confidence: 'first_claim' | 'changed' | 'revealed_on_death';
}

interface InfoDeclaration {
  playerId: PlayerId;
  characterType: CharacterType;  // 角色类型决定信息格式
  payload: InfoPayload;          // 结构化信息内容
  day: number;
  reliability: Reliability;
}

interface Nomination {
  nominator: PlayerId;
  nominee: PlayerId;
  votesFor: PlayerId[];
  votesAgainst: PlayerId[];
  passed: boolean;
  usedDeadVote: PlayerId[];      // 使用死票的人
}

interface ReasoningSnapshot {
  trustLevels: Record<PlayerId, TrustLevel>;  // 每人信任度
  demonCandidates: PlayerId[];
  confirmedGood: PlayerId[];
  contradictions: Contradiction[];
  logicChains: LogicChain[];
}

type TrustLevel = 'confirmed_good' | 'likely_good' | 'unknown' | 'suspect' | 'demon_candidate';
type Reliability = 'verified' | 'unverified' | 'possibly_tainted' | 'invalidated';
```

## 五、差异化竞争分析

### 5.1 现有工具的问题

| 工具 | 问题 |
|------|------|
| BOTC Notes | 只是结构化笔记，无推理引擎，无矛盾检测 |
| The Grim | 说书人工具为主，玩家笔记是附加功能 |
| Clocktower Notebook | 功能极简，纯文本笔记 |
| 纸笔 | 信息散落，无法快速交叉查询，复盘困难 |

### 5.2 本 App 的核心差异化

| 功能 | 现有工具 | 本 App |
|------|----------|--------|
| 信息记录 | ✅ 有 | ✅ 有（更结构化） |
| 座位图 | 部分有 | ✅ 动态收缩 + 邻座计算 |
| 矛盾检测 | ❌ 无 | ✅ **自动检测** |
| 推理引擎 | ❌ 无 | ✅ **信任度追踪 + 排除法** |
| 投票分析 | ❌ 无 | ✅ **投票模式可视化** |
| 角色矩阵 | ❌ 无 | ✅ **声明交叉矩阵** |
| 信息可靠性 | ❌ 无 | ✅ **醉/毒标记** |
| 逻辑链 | ❌ 无 | ✅ **结构化推理记录** |
| 复盘 | ❌ 无 | ✅ **时间线回放** |

### 5.3 可能的 AI 增强（Phase 2）

作为 AI Builder，你可以加入：

| AI 功能 | 说明 |
|---------|------|
| **矛盾自动分析** | LLM 分析所有信息声明，找出人类可能遗漏的逻辑冲突 |
| **假设推演** | "如果 A 是恶魔，那 B/C/D 的信息会怎样？" |
| **角色推测建议** | 基于已知信息，给出每个玩家最可能的 3 个角色 |
| **自然语言录入** | 语音/文字快速记录："Chef 说 1，Alice 声明占卜" → 自动结构化 |

## 六、技术方案建议

### 6.1 推荐技术栈

| 层 | 选择 | 理由 |
|----|------|------|
| **前端** | React Native / Flutter | 跨平台 iOS+Android |
| **状态管理** | Zustand / Riverpod | 轻量，适合本地状态 |
| **本地存储** | SQLite / WatermelonDB / Isar | 离线优先，对局不需要联网 |
| **UI 组件** | 自绘座位圆环（Canvas/SVG） | 座位图是核心交互，需要定制 |
| **AI（可选）** | 接 OpenAI/Claude API | 矛盾分析/推理建议 |

### 6.2 核心交互原则

1. **录入速度第一** — 对局中每秒都宝贵，所有输入要在 3 次点击内完成
2. **信息密度可调** — 白天讨论时可折叠次要信息，聚焦关键
3. **防误触** — 关键操作（标记死亡、处决）需要确认
4. **离线优先** — 对局中不能依赖网络
5. **暗色模式** — 线下局光线暗，暗色更护眼（也符合 BotC 哥特主题）

### 6.3 数据持久化

- 每次操作自动保存（不需要手动保存按钮）
- 支持多局历史记录
- 导出为 JSON/Markdown 供复盘
